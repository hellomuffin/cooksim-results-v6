真人研究第二批：模拟器验证与 human agent 审计

2026-09-23 · 31 位完成全程的参与者（404 局，其中 279 局有 assistant 陪同）· 对照 formal run v5 第一轮 2125 局模拟 · 数据：study_collected_v2/，脚本 study_collected_v2/tools/

这一页回答三个问题。E1：我们的哪一个指标（in-time success、efficiency、interaction quality）能复现参与者给三个 assistant 的排序；E2：参与者对模型的总体排序，与模拟器给同一批模型的排序是否一致；E3：模拟 cook（human agent）在动作、对话、犯错、听劝这几个维度上，与真人有多像——审计的设计与结果。所有数字来自同一份 tidy table 和同一个行为抽取器，页面由脚本生成。

数据与规则

收到 28 个压缩包，其中一个是 Drive 文件夹导出（含「Additional Participants」子目录）。同一台笔记本的文件夹里可以有多份 participants/<pid>.json（共用机器或重复上传），按记录里的 seed 去重后得到 36 份独立轨迹，31 份完成了三轮排序。协议与上一批相同：先独自玩 4 局（Phase 1，两道菜 × medium/hard 两张图），再由三个匿名 assistant（A/B/C）陪玩 9 局（Phase 2，三轮，每轮三个 assistant 各一局、各一道不同的菜；三轮构成 Latin square，每个 assistant 与每道菜各配一次），每轮结束排一次序。engine_rev 全部为 84e66a9f14。

沉默规则（用户，2026-09-23）。assistant 一句话都没说的局记为 invalid：该局在排序里的位置不计，但同一轮另外两局的相对顺序仍然有效。62 / 279 局（22%）触发了这条规则，按模型：Gemini 3.7 Flash 34/87、Gemini 3.1 Pro 11/69、Gemini 3 Flash 8/66、GPT-realtime 2.1 3/15、Gemini 3.1 Flash Live 3/12、GPT-5.5 2/18、GPT-5.4 mini 1/12。检查过记录：这些局里 assistant 有被正常调用（每局 10–17 次），每一次都输出 kind: silent——是模型自己选择不说话，不是 API 故障。剔除后剩 166 个有效有序对（原 279 个），来自 31 位参与者。

七个 assistant 分布在几种三人组合里：{Gemini 3 Flash, Gemini 3.1 Pro, Gemini 3.7 Flash} × 22；{Gemini 3.7 Flash, GPT-5.5, GPT-realtime 2.1} × 2；{Gemini 3.7 Flash, GPT-5.4 mini, GPT-realtime 2.1} × 2；{Gemini 3.1 Flash Live, Gemini 3.7 Flash, GPT-5.4 mini} × 1；{Gemini 3.1 Flash Live, GPT-5.5, GPT-realtime 2.1} × 1；{Gemini 3.1 Flash Live, GPT-5.4 mini, GPT-5.5} × 1；{Gemini 3.1 Pro, Gemini 3.7 Flash, GPT-5.5} × 1；{Gemini 3.1 Flash Live, Gemini 3.7 Flash, GPT-5.5} × 1。Gemini 3.7 Flash 出现在大多数组合里，是把各组合连成一张图的桥。

E1 · 我们的指标能否复现参与者的排序

一个 assistant 在一局里得到一个分数 s；参与者的一次排序 A>B>C 给出三个有序对。对一种打分方式，

agreement = (1/N) Σ有效对 [ 1(swinner > sloser) + ½·1(swinner = sloser) ]

0.5 是随机；同样的 166 对上随机分数的中位数 0.500、95 分位 0.566、99 分位 0.596，高于 0.60 才算说明了什么。「exact rounds」是整轮三者顺序完全对上的轮数（沉默局剔除后一轮可能只剩两局）。区间是按参与者做的 bootstrap 95%。

先说一个混淆。一轮里三个 assistant 各配一道不同的菜，参与者更偏爱那个抽到简单菜的 assistant：用「菜的 reference ticks 越小越好」这个与 assistant 无关的分数去预测排序，逐轮一致率 0.608（CI 0.54–0.68），有效对里简单菜一方赢了 101 次、难菜一方赢 65 次。逐轮（per-round）一致率因此都带着这层菜的影响；「动作 tick 少者优」的 0.66 有一部分就是它。Latin square 让这一混淆在参与者层面抵消：每个 assistant 与每道菜各配一次，于是第二组列以（参与者 × 模型对）为单位——人的偏好 = 三轮里 i 排在 j 前面的次数，指标 = i 的各局均值 vs j 的各局均值——71 个单位，来自 30 人；这一层上「菜简单者优」降到 0.57（CI 0.45–0.70），即随机。

解读。效率族（S、TT、CC、E）在两个层面都与随机无法区分：S 饱和（有 assistant 陪同时 93% 的局在时限内做成，沉默局甚至 97%），TT 量的是这个人自己的手速，CC 只惩罚说话压在动作上；把 S、TT、CC 用 0…5 的整数任意加权搜遍，最好也只有 0.608（权重 (0, 1, 3)），落在随机分数经同样搜索能达到的范围内。能跟上人的判断的是两样东西：interaction quality rubric（AQ）——逐轮 0.630（CI 0.55–0.71），参与者层 0.641（CI 0.49–0.76）——和一个更朴素的量：assistant 发出的 false alarm 数，逐轮 0.672（CI 0.61–0.73），参与者层 0.634（CI 0.52–0.72）。两者说的是一回事：真人判断 assistant 好坏，主要看它有没有错怪自己。这批数据里 assistant 对真人发出的 491 次警告，245 次是 false alarm（50%），只有 41 次说对（其余 205 次不可核验）。上一批的结论「效率族失效、AQ 有效」在人数翻倍、模型从 5 个到 7 个之后成立。

关于「这是不是 Elo」。参与者那一侧不是 Elo：Elo 是对一串按时间到来的对局做在线更新的近似，我们的对局是一次性全在手上的，直接拟合的是它的批量版本 Bradley–Terry（E2 用它）。指标那一侧根本不需要排名模型——每局有一个绝对分数，问题只是这个分数的大小顺序与人的顺序有多一致，所以用有序对一致率。

E2 · 参与者对模型的排序 vs 模拟器对同一批模型的排序

人这一侧用 Bradley–Terry：P(i 胜 j) = esi / (esi + esj)，对 166 个有效有序对做 MM 迭代拟合（每对模型各加半场虚拟胜负作弱先验），名次区间是按参与者 bootstrap 的 95%。

模拟器这一侧：formal run v5 的 roster 与真人研究只共享两个模型（GPT-realtime 2.1、Gemini 3.1 Pro），所以用 sweep v4（2026-09-08，同 10 个厨房、9 个 assistant × 3 persona × 50 局 = 1,350 局，同一 rubric）——它含真人研究七个模型中的六个（缺 Gemini 3 Flash）。Kendall τ 在这六个模型上比较两侧的顺序：

解读。人的顺序是 GPT-realtime 2.1 > GPT-5.4 mini > Gemini 3.7 Flash > GPT-5.5 > Gemini 3.1 Flash Live > Gemini 3 Flash > Gemini 3.1 Pro。模拟器的 in-time success 与 AQ 都给出 τ = +0.47：两侧都把 GPT-realtime 2.1 放在最前、把 Gemini 3.1 Pro 和 Gemini 3.1 Flash Live 放在最后，分歧在中段（人把 GPT-5.4 mini 排第二，模拟器排第四；人把 GPT-5.5 排第四，模拟器排第二——这两款各只有十几场，名次区间 1–6 / 1–7，不足以说谁对）。效率 E 与人的顺序相反（τ = -0.73）：E 只在做成的局上定义、又奖励少说话（CC），于是把最沉默的 Gemini 3.1 Pro 排到第一，而真人把它排到最后。这与 E1 的结论是同一件事的两面——效率族度量的不是人在乎的东西。

局限：GPT 三款样本少；sweep v4 是 9 月 8 日的引擎和 cook prompt，与真人研究 app（84e66a9f14）不是同一版；formal run 上只有两个模型可比（GPT-realtime 2.1 在 formal run 的 in-time success 0.41 vs Gemini 3.1 Pro 0.19，方向与人一致）。

E3 · human agent 审计：模拟 cook 像不像真人

设计

目标是把「像」拆成可测的维度，每个维度用同一段代码在两侧算（真人的记录和模拟的记录都带逐 tick 世界状态 .states.jsonl，所以动作与犯错都从状态读，与各自的日志格式无关）。模拟侧只算 cook 自己的 tick：engine 强制接管的动作（kind 不是 vlm_fix）和注入窗口（injected_at → released_at）被遮掉；SYSTEM TASK 脚本化的发言（探测问题、提醒请求、plan change 宣布）剔除。对照组：REAL assisted（有 assistant 且 assistant 开过口）、REAL solo（Phase 1）、SIM formal（formal run v5 第一轮，18 个 assistant × 3 persona，与真人相同的 10 个厨房）、SIM silent asst（MMDuet2 座位——它从不说话，因此是模拟里的「无人相助」对照，但仍有错误注入）。

结果

真人侧「改正」= app 判为 correct 的 flag 之后，对应的世界真值谓词在 30 tick 内消失；模拟侧 = 被正确 flag 的注入错误随后被 cook 放弃（engine 的 prevented）。两个定义不完全同构（模拟侧的错误是 engine 强推的、放弃要靠 assistant 说服；真人侧的错误是自己犯的），但方向一致：模拟 cook 比真人更听劝——novice 0.73、expert 0.53，真人 0.40。按错误类型，模拟 cook 对 mis_prep（138/178）、forget_next_step（107/146）几乎有劝必改，对 add_foreign（3/16）、misidentify（2/15）、omit_subgoal（4/13）几乎不改——这三种是「hard」接管，改不改由 engine 决定，不是 cook 的性格。

发现

F1 · 身体节奏：像的部分和不像的部分。第一次用火的 tick 真人 55、模拟 52——上一批「真人开局要摸索」的差距已经没有了（这批真人是第二、三轮的老手，模拟 baseline/expert 41/37，novice 80）。walk 占比 0.35 vs 0.32 也接近。不像的是 idle：真人 0.17，模拟 0.31（novice 0.42）；并行度真人 0.21、模拟 0.16。上一批的 F1（执行器每条命令吃一个死 tick）没有改，这仍是 idle 差距的主要来源。

F2 · 热源：模拟 cook 仍然让熟食等到冒烟。熟食在火上的等待真人 12.7 tick、模拟 26.9（tight pace 的冒烟线是 25）；注入窗口外自己冒烟的局，真人 29/217，模拟 1204/2125。表 6 用同一套谓词看 onset：smoking 每 100 tick 模拟 0.36 次、真人 0.09（独自时 0.15）。有意思的是 done-food-on-heat 的 onset 真人反而更多（0.91 vs 0.55）：真人也让菜熟在锅里，但很快就去舀（13 tick），模拟 cook 一放就是 27。上一批的 F2 原因（先把菜全做完、最后拿盘）仍在。

F3 · 犯的错：种类对得上，频率除冒烟外也对得上。表 6：plate wrong state 真人 0.03 / 模拟 0.03，plate order 真人 0.05 / 模拟 0.06（独自时真人 0.09），foreign item 真人几乎没有（0.00）、模拟 0.02。真人自己会犯的主要就是顺序错和放生的，与我们错误库里的 wrong_order / serve_raw / mis_prep 对应；真人从不放菜谱外的东西，add_foreign 只在注入时出现。

F4 · 对话量：差距还是 40 倍。自发句数每 100 tick 真人 0.40、模拟 16.8；回应 assistant 的比例真人 0.02、模拟 0.79。12 / 31 位参与者在九局陪玩里一个字都没说，23 位只在 ≤2 局里开过口。每句词数已经接近（真人 6.1，模拟 7.3）。

F5 · 说的内容：播报下一步仍是模拟特有的。表 7：「narrates own next action」真人 2%、模拟 24%。两侧相似的是「asks where / what to do」（20% vs 16%）和「corrects the assistant」（23% vs 17%）。真人独有的：打招呼 9%、问「你是什么模型」2%、不满 3%、策略问题 6%，以及 5% 的「tell me when the steak is ready」式主动请求——真人自发提出了我们 Q10 那类请求，这是对 benchmark 设计的一个小验证。

F6 · 听劝：拿东西的顺从度一样，改错的顺从度模拟更高。表 8：点名食材 15 tick 内拿起，真人 0.28、模拟 0.26，未点名对照 0.11 / 0.09——完全一致；反驳占比 0.23 / 0.22 也一致。被正确警告后改正：真人 0.40，模拟 0.66。

F7 · persona 拨盘造出的差异比真人个体间的差异大得多，而真人按问卷分组几乎没有差异。表 9：q1、q3 各组的 S 在 0.88–0.98、CC 在 0.72–0.85 之间，发言量、idle、首次用火没有单调关系；模拟的 novice 与 expert 在 idle（0.42 vs 0.26）、首次用火（80 vs 37）、发言量（21 vs 12）上差一倍。表 9b：真人个体的 idle SD 0.07（极差 0.05–0.42），persona 极差 0.16；真人的发言量极差 0–2.4 句/100t，persona 12–21。结论：persona 造出的是「更极端的模拟 cook」之间的差异，不是真人之间那种差异；真人的差异主要在动作节奏，不在说话。

F8 · 真人跨局学习，模拟 cook 不学。真人独自四局的 in-time success 0.59 → 0.74 → 0.87 → 0.81；陪玩三轮 S 0.91 / 0.90 / 0.96，idle 0.21 / 0.16 / 0.15，发言 0.67 / 0.42 / 0.15 句/100t——越玩越熟、越玩越不说话。模拟 cook 每局从零开始，也没有「新手第一局」的状态；这批真人的 Phase 2 是熟手，所以对照模拟时 novice persona 反而是最不像的。

F9 · 结果层面还缺一个对照。真人独自做成率（S）四局均值 0.75，有 assistant 时 0.93；模拟侧所有局都带错误注入（≥ 半数是毁菜的），won 只有 31%，无法与真人比较「独自做成率」。需要一次 cook-only、无注入、无 assistant 的干净 run（10 个厨房 × 3 persona × 2 = 60 局）。

待裁决

  1. R1 · 干净对照 run。60 局 cook-only（Gemini 3.7 Flash cook，无注入、无 assistant），补上表 4 的第 ⑧ 维度。成本约 60 × 4 分钟的 API cook 调用、一台渲染机一小时；未启动，等指示。
  2. R2 · 沉默局怎么进 benchmark 口径。22% 的真人局 assistant 全程沉默（Gemini 3.7 Flash 34/87），真人在这些局里做成率 97%——比有话说时还高。本页按用户规则剔除；benchmark 里 AQ 对沉默局记 0 的规则要不要沿用，请定。
  3. R3 · 模拟 cook 的发言率与「播报下一步」。40 倍的量差和 24% 的播报没有随 cook prompt 的修改减少（上一批 35%）。是否再改 prompt（禁止在没有被问的情况下说自己在做什么），还是接受为模拟的固有形态。
  4. R4 · 执行器死 tick 与先做菜后拿盘。上一批 F1/F2 的两个引擎问题仍在（idle 0.31 vs 0.17，熟食等待 27 vs 13 tick）。这是 benchmark 里「leave_unattended 之外的冒烟」的来源。
  5. R5 · AQ 的 judge。本页 AQ 由两个 judge 各评一次后平均（上一批的裁定）；单 judge 的一致率 Gemini 0.64 / GPT 0.55，平均后 0.63。formal run 的 sq_v4 目前是 gpt-main 单 judge——要不要对 formal run 也补第二个 judge。
