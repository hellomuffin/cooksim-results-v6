0 · 这是什么、为什么跑三遍

评测对象。 九个模型坐同一个 assistant 座位：看厨师做菜，可以随时说话，按四件事打分 —— 菜有没有做成、engine 注入的错误有没有被抓到、厨师的问题答得对不对、「好了叫我」这类 proactive request 报得及不及时。每个模型跑同样的 10 局（每个 recipe tier × map 各一局，persona 轮换），各跑三遍。

为什么三遍。 单跑一遍几乎说明不了 detection：同一个模型在同一局里，这一遍抓到两个错，下一遍一个都不抓。这次的重点是离散度，不是排行榜。per-model 的三遍展开（每个分数的 r1/r2/r3 均值、标准差、10 局里有几局三遍完全相同、以及 pass@3 / pass^3）在 tmp/local_pass3_logs/FINAL_consistency.md。

读法

  • GPT-6 Astra 把任务做成得最好、问题答得最好（won 0.97、QA 0.79、proactive 0.73），但延迟倒数第二（6.3 tick），detection 只算中游（0.36）。
  • gpt-realtime-2.1（polled 模式）是全场最强的 detector：caught 0.48，其它模型 0.26–0.39；in-time success 与 Astra 并列第一；代价是 API 模型里最差的答题能力（QA 0.38）。
  • Muse Glimmer 30B（本地）的 detection 超过除 gpt-realtime 外的所有 API 模型（caught 0.39），延迟只有 Astra 的一半。
  • Qwen3.8-27B 是「话少但准」的那个：30 局里只有 1 次误指控（0.03/局），同时在 20 局里都 flag 过。
  • Gemini 3.1 Pro 是 false alarm 的异常值（1.77/局），也是最慢的（7.4 tick）。
  • Molmo2-8B 基本不参与 detection（caught 0.04、QA 0.04），与它 setup bench 的表现一致。
  • fired 在所有模型都是 0.84–0.89：benchmark 注入的错误与谁在看无关，差异来自模型和厨师。

2 · 两个 streaming 模型（都跑 polled）恰好是两个极端

两个都用 polled 模式跑（harness 主动问，它们自己的 speak decision 还没接上），结果落在同一根轴的两端：

  • gpt-realtime-2.1：caught 0.48 / prevented 0.46，全场最高；代价是 0.97 FA/局（0.37 invented + 0.60 wrong-moment）和 API 模型里最弱的 QA（0.38）。
  • gemini-3.1-flash-live-preview：全场最快（2.0 tick，30 局完全一致），won 0.90；但话最松 —— 30 局 137 个 flag、1.97 FA/局（1.27 invented + 0.70 wrong-moment），整轮只有 4 个 flag 被判 valid，caught 只有 0.26。它拿到的检测分大多是 early_correct 或 late：说对了事、说错了时候。（它在前 15 局看起来 in-time success 0.92 全场第一，跑满 30 局后回落到 0.77 —— 所以中途的数字从不当结果发布。）

这一对正好是把 native arm 做完的理由：polled 协议已经能产出全场最强的 detector 和最爱乱说的那个，而「什么时候该说话」本来就该由 native speak decision 管。

3 · 必须一起读的 caveat

  1. detection 是最不可复现的分数。 多数模型在同一局的三遍里 catch rate 都不一样，只有三遍均值有意义。
  2. false alarm 其实是两件事。 flag 指的错确实触发过、只是落在窗口外，今天也判 false_alarm。各模型 invented / wrong-moment：Live 38/21、Gemini 3.1 Pro 27/26、MiniCPM-o 24/7、Gemini 3.8 Flash 14/5、gpt-realtime 11/18、Astra 10/5、Muse 7/8、Molmo2 4/0、Qwen 1/0。永远读拆开的两列。
  3. prevented 比字面弱。 它只表示助手说话之后厨师没犯这个错，不要求助手指出了什么。逐条读了三个案例：一个是真的（gpt-realtime 把卡住的厨师劝动了）；一个是厨师被同一句话重复七遍后妥协（MiniCPM-o，全程没有任何 flag）；一个跟在助手自己说错的指令后面（Molmo2 让厨师去拿 Steak Frites 不需要的 bun，厨师反问，错误就此作废）。三例的 error entry 都没有 flag。
  4. benchmark 侧与模型无关：同样的错误在每一遍都触发（fired 0.84–0.89，10 局里 9–10 局三遍完全相同）。
  5. 这一轮做的评分修正（全部离线、对所有模型一视同仁、每一条都对着 transcript 逐条核过并写了回归测试）：回复归属到它真正回答的那个问题；episode 最后 10 tick 内才问、来不及答的问题不计分；「我是先切的 X 吗」的 ground truth 改从逐 tick 状态记录重算；对 recipe 根本不会切的食材问「切没切」的问题不计分；三类不是 alert 的句子不再算 proactive alert（带 scoop 的承诺、点名熟食的否认、计划步骤/前缀）。
  6. 顺带查出的 suite 缺陷（这次之后再修）：448 个问题里 114 个不可评分 —— 60 个问在 episode 最后 10 tick（落在助手自己的延迟里），54 个是对不会切的食材问「切没切」。其余 334 个：correct 131 / partial 12 / incorrect 70 / evasive 110 / 未答 11。
  7. 我自己造成、已修复的一个瑕疵：有约一小时我把 model server 钉在固定 CPU core 上，Qwen 和 Molmo2 的图像预处理因此每次回复慢了约 1 个计费 tick。受影响的 10 局全部在窗口外重跑：没有一局变慢，4 局更快，3 局少花 1 个 tick；被丢弃的原始记录连同逐 tick 状态留在 tmp/local_pass3_quarantine_pinwindow/。
  8. 没跑的模型：GLM-4.6V-Flash（权重和 serve 脚本都就绪，但在三台 model server 占满 /weka 的情况下 12 分钟连模型都没加载完，硬截止前停掉，GPU 留空而不是拖慢正在计时的 lane）；Proact-VL（权重需要账号本人接受学术条款）；Streamo（只有代码没有权重）；Claude Opus 5 与阿里系（本机还没有 key）。两个 streaming 模型只跑了 polled，native arm 设计好了但还没做。

4 · 接下来该做什么

  1. 把 native streaming arm 做完。 polled 模式下已经出现「最强 detector」和「最爱乱说」两端，而这正是 native speak decision 该管的行为。
  2. 修两个 suite 缺陷：问题被排在 episode 末尾；prep 问题一律写成「did I chop X」。两个都是 question generator 的改动。
  3. 决定「说对了错、但落在窗口外」算不算 false alarm。 今天算。改判会移动每个模型的 catch rate，所以需要单独一轮核对，不能顺手改。
  4. 补跑 GLM-4.6V-Flash（机器空闲时是个小活），以及拿到 key 之后的 Claude Opus 5 和阿里系模型。
  5. detection 永远报三遍均值，不要报单跑 —— 这是这次最主要的方法学结论。
