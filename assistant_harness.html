1 · What the assistant seat is

The assistant is the only component we do not build, and everything in the harness exists to make sure the thing we measure is the model rather than its plumbing. Four invariants define the seat; a port that keeps them produces numbers comparable in kind with ours, and a port that drops one does not.

  • It observes a rendering only. Frames plus the public conversation. No symbolic state, no scene graph, no affordances, no schedule, no verdicts, no engine channel of any kind.
  • It cannot act. Its only output that reaches the world is a sentence spoken to the person. A structured mistake flag goes to the engine for verdicting and for the takeover-release rule, and is never shown to the person and never changes an object.
  • It is polled on a fixed schedule — every K ticks, with a fixed-length frame window — so that "how often it could speak" is a property of the protocol and not of the model's latency.
  • Its prompt is audited at run start. Assertions run on the composed prompt the model actually receives, not on templates: no instance ids, no coordinates, no grading vocabulary. A violation aborts the run before it spends budget.

2 · The interface

What arrives each poll

  • the current tick;
  • the last W rendered frames, oldest first (kitchen: 8 frames at 1/tick, polled every 2 ticks; phone: 2 frames; household: 8 composite frames at 1/s);
  • the full public conversation with tick stamps, and the person's latest utterance;
  • its own previous output — the only memory the harness gives it, which is deliberate: memory management is part of what is being measured;
  • a static system prompt: the task instruction, the person's public plan, the world's rules (what each station accepts, what a widget kind does), and the person's questionnaire answers.

What it must return

{
  "text": "what it says out loud; empty string = stay silent",
  "flag": null | {"error": "<one label from the engine's fixed taxonomy>"},
  "cook_progress": {            // its own tracking; never graded directly
     "completed": [...], "current": [...], "future": [...] },
  "goal_change": null | "<its record of an announced plan change>"
}

Only text crosses to the person. The kitchen's exact system prompt and reply schema are published verbatim on the prompts page; the household's are rendered from its live harness in the observation-contract page. Copy the shape, replace the world rules and the label vocabulary.

Schema compliance is a measured property, not a harness problem. Some models return prose, or a bare inner object instead of the envelope. The harness retries three times and then records an empty reply — it never repairs the output. Two of the nine models we ran are effectively disqualified by this alone, and that is a result about them.

3 · Backends

All four backends implement one method, so the rollout calls a single funnel: sup_call(system, user, frames) -> dict. The wrapper adds retries with backoff, per-call latency and token accounting, and session handling for the streaming APIs.

The four backends. tools/assistant_backend.py wraps any backend from tools/controller_eval.py; the rollout recognises it by its .sup_call attribute.

liveGemini Live sessionstreaming-native Geminione session per episode; the system text is taken once, at open
realtimeOpenAI Realtime WebSocketstreaming-native GPTone session per episode, output_modalities=["text"]; see the token warning in §11

To add a fifth backend, implement call(system, user, frames) -> (dict, meta) returning parsed JSON plus a meta dict with latency_ms, prompt_tokens, completion_tokens, and register it in make_assistant(). Nothing else in the harness needs to change. If the model holds a session, expose reset_episode(system) and the wrapper will open it once per episode instead of resending the system text every turn.

4.1 · Serving the three open-weight assistants

Three of the nine seats are open-weight models we serve ourselves; the harness only ever sees an OpenAI-compatible endpoint, so these are the seats a port can run with no API key at all. Everything below is what we actually ran, and every command lives in the repo beside its logs (local_models/<model>/{SETUP.md,serve.sh,smoke.py,RESULTS.md}).

Two rules before any of it. (1) Pick the vLLM build from your driver, not from the changelog. This box runs driver 570 / CUDA 12.8, so the newest usable PyPI wheel is vllm==0.19.1 (torch 2.10.0+cu128); vLLM ≥ 0.20 pins a cu130 torch that needs driver ≥ 580 and fails at import with libcudart.so.13: cannot open shared object file. If a model needs a nightly, take the cu129 variant explicitly. (2) One private environment and HF cache per model (envs/<model>, HF_HOME=hf_cache/<model>) — the three stacks pin conflicting transformers versions, and installing into a shared env is how you lose a working server. Weights are pre-downloaded and every server runs with HF_HUB_OFFLINE=1.

The three servers. Ports are fixed because the harness flags name them; one GPU each; all bind to localhost.

qwen-27b — Qwen3.8-27B on vLLM

ROOT=<your root>;  export HF_HOME=$ROOT/hf_cache/qwen
/opt/conda/bin/python3 -m venv $ROOT/envs/qwen
$ROOT/envs/qwen/bin/pip install "vllm==0.19.1" openai pillow requests
hf download Qwen/Qwen3.8-27B                       # 52 GB; 9B and 2B siblings also work

CUDA_VISIBLE_DEVICES=3 HF_HUB_OFFLINE=1 $ROOT/envs/qwen/bin/vllm serve Qwen/Qwen3.8-27B \
    --served-model-name qwen-27b --host 127.0.0.1 --port 18300 \
    --tensor-parallel-size 1 --dtype auto --max-model-len 32768 --max-num-seqs 4 \
    --limit-mm-per-prompt '{"image": 8}' --gpu-memory-utilization 0.90 \
    --reasoning-parser qwen3 --default-chat-template-kwargs '{"enable_thinking": false}'

Why those last two flags. The harness sends no chat_template_kwargs, so thinking has to be turned off server-wide or every call pays for a <think> block; --reasoning-parser qwen3 keeps that block out of message.content if you ever turn it back on (THINK=1 bash serve.sh 27b). --limit-mm-per-prompt '{"image": 8}' must match the frame window or the server rejects the poll. Harness side: --assist-backend openai --assist-model qwen-27b --assist-base-url http://127.0.0.1:18300/v1 (default request profile).

minicpmo — MiniCPM-o 4.5 (AWQ) on vLLM

export HF_HOME=$ROOT/hf_cache/minicpmo
/opt/conda/bin/python3 -m venv $ROOT/envs/minicpmo-vllm
$ROOT/envs/minicpmo-vllm/bin/pip install "vllm==0.19.1" "transformers==4.57.6" openai pillow
hf download openbmb/MiniCPM-o-4_5-awq --exclude "assets/*"      # 8 GB; bf16 repo also serves

MODEL_DIR=$(ls -d $HF_HOME/hub/models--openbmb--MiniCPM-o-4_5-awq/snapshots/*/ | head -1)
CUDA_VISIBLE_DEVICES=2 HF_HUB_OFFLINE=1 $ROOT/envs/minicpmo-vllm/bin/vllm serve "$MODEL_DIR" \
    --served-model-name minicpmo --host 127.0.0.1 --port 18100 \
    --dtype bfloat16 --trust-remote-code --max-model-len 8192 --max-num-seqs 4 \
    --gpu-memory-utilization 0.85 --enable-prefix-caching \
    --limit-mm-per-prompt '{"image": 8, "video": 0, "audio": 0}' \
    --mm-processor-kwargs '{"max_slice_nums": 1}'

transformers must stay below 5 — the model ships remote code written for the 4.x processor API, and a 5.x env fails to load it. max_slice_nums is the resolution knob: 1 gives 64 vision tokens per frame and 0.76 s per 8-frame call, 9 turns on HD slicing (320 tokens per frame, 1.63 s) and fixed a direction error we saw at the low setting — a real trade the port has to make and record. The context is only 8k, which is why this seat runs --assist-max-tokens 2000 and the minicpmo profile (temperature 0.1, thinking off, images before text, which its model card requires).

museglimmer — Muse Glimmer 30B INT4 on a vLLM nightly

export HF_HOME=$ROOT/hf_cache/museglimmer
uv venv --python 3.12 $ROOT/envs/museglimmer
uv pip install --python $ROOT/envs/museglimmer/bin/python --prerelease=allow -U \
    "vllm==0.27.2rc1.dev193+gaa9903490.cu129" --torch-backend=cu129 \
    --extra-index-url https://wheels.vllm.ai/nightly/cu129
hf download RedHatAI/Muse-Glimmer-30B-INT4
hf download meta-models/Muse-Glimmer-30B-assistant          # +5 GB DFlash drafter, ~2x decode

CUDA_VISIBLE_DEVICES=1 HF_HUB_OFFLINE=1 $ROOT/envs/museglimmer/bin/vllm serve RedHatAI/Muse-Glimmer-30B-INT4 \
    --served-model-name museglimmer --host 127.0.0.1 --port 18200 \
    --tensor-parallel-size 1 --dtype auto --max-model-len 32768 --max-num-seqs 4 \
    --limit-mm-per-prompt '{"image": 8}' --gpu-memory-utilization 0.90 \
    --reasoning-parser muse_glimmer \
    --speculative-config '{"method":"dflash","model":"meta-models/Muse-Glimmer-30B-assistant","num_speculative_tokens":15}'

Why a nightly. Muse Glimmer support landed after the last release wheel; the plain nightly is built for CUDA 13 and will not import on driver 570, so the cu129 index and the pinned build above are the working combination. Why the odd request profile. The RedHatAI chat template appends "Reasoning strength: high." to whatever system prompt you send, so the only reliable knob is the request field chat_template_kwargs={"reasoning_strength": "low"}; the museglimmer-nothink profile sends that and prefills an empty assistant turn (add_generation_prompt=false, continue_final_message=true), which cuts a reply from ~450 completion tokens to ~125 and the call from 33 s to 9.4 s. --assist-image-scale 0.5 is there because a full-resolution composite frame does not fit the context at eight frames.

Prove each server before you sweep

curl -s http://127.0.0.1:18300/v1/models | head -c 200      # the server answers, name matches --assist-model
$ROOT/envs/qwen/bin/python local_models/qwen/smoke.py --model qwen-27b --out /tmp/qwen_smoke.json

The per-model smoke.py sends the real shape — eight 800×580 frames plus the system prompt — and records latency, token counts and whether the reply parsed as JSON. A seat that fails the smoke test will fail 1,515 times in a sweep. Then run §7.1 with --assist-base-url pointed at the port and check the same five fields; only then start launch_v3.sh local.

5 · Request profiles

Sampling is a property of the model, not of the harness: imposing one temperature on every model is a way of testing your own defaults. A profile is a named bundle of request fields applied by the OpenAI-compatible backend.

profilewhat it setswhy
defaulttemperature 0.2generic servers
gpt5temperature omitted; max_completion_tokens instead of max_tokens; reasoning_effort: lowGPT-5.x rejects a temperature and prices reasoning as a request field; low effort is the latency lever
minicpmotemperature 0.1; enable_thinking: false; images before the text partfrom the model card; images-first was 30/30 valid JSON in the smoke test, images-last was not
museglimmer-nothinkT 1.0, top_p 0.95, top_k 64; reasoning_strength: low; assistant-turn prefill with continue_final_messageits own guide forbids greedy decoding; the prefill suppresses a reasoning preamble, ~125 completion tokens instead of ~450

Adding a profile is a dict entry in PROFILES (tools/controller_eval.py). Rule of thumb: read the model's own guide, copy its recommended sampling, and record the profile name in the report so the setting travels with the number.

7 · Launch recipes

7.1 One episode, to prove the seat works

Always do this before a sweep. It costs one episode and catches every wiring error.

cd <engine root>
source tmp/present/env.sh                      # $PY, Gemini creds
export OPENAI_API_KEY=$(cat ~/.openai_key)
export COOKSIM_PACE=tight COOKSIM_CASES=tmp/interact_eval/cases_composite_v3.json
export GEMINI_MODEL=gemini-3.7-flash           # the PERSON's voice

$PY tools/e2e_stepin_rollout.py \
    --case b3_easy_nops_medium_map_1 --persona-v2 baseline \
    --paradigm hardsoft --sup-obs frames --out /tmp/smoke.json \
    --assist-backend openai --assist-model gpt-5.5 \
    --assist-base-url https://api.openai.com/v1 --assist-profile gpt5

Then read /tmp/smoke.json and check five things: assistant_backend.calls is non-zero; the conversation contains assistant lines; injections[].injected is true; every flag carries a verdict; and engine_rev is stamped.

7.2 One model over the whole suite

$PY tools/run_assist_bench.py --tag gpt-5.5 --sup-obs frames --workers 8 \
    --persona-v2 baseline classic_novice classic_expert \
    --out-root tmp/assist_bench_v3/frames \
    --assist-backend openai --assist-model gpt-5.5 \
    --assist-base-url https://api.openai.com/v1 --assist-profile gpt5

The runner is a process-per-episode worker pool: one rollout owns one browser page, N run in parallel, and it is resume-safe — an episode whose output JSON exists is skipped, so the same command continues a partial sweep after any interruption. Logs go to local disk (--log-dir), never to network storage, because a wedged network directory takes the whole sweep with it. --reverse works the queue from the end, so a second runner can be pointed at the same cell without collision.

7.3 All the models

bash tmp/assist_bench/launch_v3.sh api      # the six API assistants
bash tmp/assist_bench/launch_v3.sh local    # the three local ones (servers must be up)
bash tmp/assist_bench/launch_v3.sh silent   # the floor
bash tmp/assist_bench/launch_v3.sh one my-model 6 \
     --assist-backend openai --assist-model my-model \
     --assist-base-url http://127.0.0.1:18400/v1        # a single new entrant

Each launcher line detaches with setsid nohup, so runners survive a lost shell. Check progress with pgrep -fc run_assist_bench and the per-runner logs under /tmp/assist_bench_logs/.

8 · Scoring, judging and publishing

Scoring is offline and idempotent: it reads the episode JSONs and writes one file, so it can be re-run at any time, including while the sweep is still going.

export ASSIST_ROOT=tmp/assist_bench_v3

$PY tools/regrade_qa.py --workers 8        # judge the cook's questions against engine truth
$PY tools/regrade_proactive.py             # score standing-request timing
$PY tools/eval_v2_sweep.py                 # outcomes, efficiency, detection -> eval_v2.json
$PY tools/aggregate_v2.py                  # per-cell aggregates
$PY tools/sq_v4_score.py --workers 6       # the round-level guidance rubric (the one judged score)

$PY tools/build_suite_v3_page.py ../<site>/suite_v3_results.html
$PY tools/build_metrics_page.py   ../<site>/metrics.html

Or run the whole loop — judge, score, aggregate, build, push — with bash tmp/assist_bench/v3_cycle.sh, which is what republishes the results page every half hour.

Judge policy, if you copy the rubric. The judge must be from a different model family than the assistant under test (we use flash-tier judges in both directions and average the two for local models). Grade per conversation round, not per episode: one line, its reply, and what the person did next. Let the engine decide the two items a fluent model can talk its way past — is a claim about the world true, and could the advised action be started in that state. And publish the inter-judge agreement beside the score; ours is r = 0.51 with 78.1% agreement on the binary must-item verdict, which is exactly why that score carries no headline claim.

9 · What must be held fixed

Everything below is a way for two numbers to stop being comparable. Hold them fixed, or report them as a factor.

  • The observation setting. Frames only. Text-state settings exist in the harness as upper-bound controls and are not the benchmark.
  • The person's model. One model in the voice for the whole sweep (a voice swap moves outcomes: in our slice, in-time success 0.54 against 0.33 with detection nearly unchanged).
  • The suite and the physics preset, both stamped in every report along with the engine revision; the results page filters on the revision so a mixed corpus cannot be published by accident.
  • The poll schedule and frame window. A model that is polled more often is a different experiment.
  • The silent floor, run over the same episodes and personas, in every table.
  • The validity gates. An episode where the injection never fired, or whose window was never anchored, is not measured — never a zero.

10 · Adding a new assistant

Checklist

  1. Pick the backend (gemini / openai / live / realtime); for anything self-hosted, stand up an OpenAI-compatible server that accepts image parts.
  2. Read the model's guide and add a PROFILES entry if its sampling or reply budget differs from the default. Do not skip this: two of our nine needed it to produce valid JSON at all.
  3. Run the one-episode smoke test (§7.1). Confirm valid JSON, non-empty text on at least some turns, and a flag that carries a verdict.
  4. Check the composed-prompt audit passed in the log — it aborts the run if the prompt leaks ids, coordinates or grading terms.
  5. Measure a schema-compliance rate over ~10 episodes. Below ~90% valid replies the model is not testable in this seat, and that is a finding to report, not a bug to patch.
  6. Estimate cost from §11: calls/episode × tokens/call × 150 episodes per persona-crossed sweep.
  7. Choose workers from the rate limit or the GPU, start with 4, and watch for 429s in the runner log.
  8. Launch the full sweep, then score. Re-run scoring as it fills; nothing needs to wait for completion.

Three things worth knowing before you budget:

  • Frames dominate the prompt. Roughly a million prompt tokens per episode for an 8-frame window at 0.5 Hz. Shrinking the window or the image is the only real lever, and both change the experiment, so change them for everyone or for no one.
  • Session APIs can bill an order of magnitude more. The realtime seat reports 11.4 M prompt tokens per episode because the session re-sends accumulated context; it is the same protocol from the model's point of view and a very different invoice.
  • A full crossing is 150 episodes per assistant (50 episodes × 3 personas). Nine assistants plus the floor is what produced the 1,344 completed rollouts, at roughly a day of wall clock with the worker counts in §4.
