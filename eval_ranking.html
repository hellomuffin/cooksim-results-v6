Does seeing more make it better?

One scenario — the cook plates in the wrong order and the outcome is already sealed — run for two cooks, two observation tiers and two injection paradigms. Seven metrics per episode, reported separately and unweighted — there is no overall score.

How every episode on this page was produced — one configuration, checked mechanically by tools/config_audit.py (30 checks) before any of it ran.
  • Harness: e2e_stepin_rollout.py — nothing is scripted. The error or intent is injected covertly into the cook's plan; the assistant must notice it from what it sees.
  • Pause treatment: speaking costs the cook game time, listening is free. The world keeps running while anyone talks — the pan keeps cooking.
  • Observation: one side-by-side composite per tick — top-down on the LEFT (the coordinate frame), the cook's first-person view on the RIGHT — rendered photoreal.
  • Every episode ran twice, once per observation tier, and both are shown.
  • Video: 1.5× playback (1 tick = 0.8s) with the speech sped by the same factor, the way a player speeds audio when you watch at 1.5×. The frame never holds: a caption you read is spoken over ticks that are still advancing.
Every metric sentence, sub-rubric wording and formula on this page is taken from the code that produced the numbers (tools/eval_assistant.py, tools/eval_judge.py); nothing here is a re-description, and the build refuses to write the page if any metric fails to reproduce from the rubrics drawn under it.

Seven metrics, reported separately

There is no overall score on this page. Each episode is reported as seven independent readings, every one of them normalised to [0,1] with 1 always better — as if every weight were 1. Nothing is multiplied by anything, and nothing is added up.

That is a deliberate change. The seven ask genuinely different questions — did the dish get made, how long did it take, did the assistant cry wolf, how much did it intrude, did it convince the cook, how did the cook feel, was anyone put at risk — and there is no exchange rate between them that is not simply asserted. The previous version of this page asserted one: a hand-written per-persona weight table that produced a single composite, which then had to be explained away every time it disagreed with the reading underneath it. Reporting the seven side by side says less, and all of what it says is measured.

Because no persona-specific weighting is applied any more, a metric means the same thing in every cell of the table below and a column can be read straight down. The two cooks are still shown in separate sections — the persona is an experimental condition, and the assistant faces a different problem in each — but they are now on one scale and may be compared directly.

Normalisation is against fixed reference constants, not against the other episodes on this page, so a value does not move when a neighbouring run changes. Underneath each metric, every sub-rubric that produced it gets its own bar, its raw measured value, and the reference constants it was scored against — so a number can be traced from “C2 = 0.14” down to “132 words” without leaving the page. Those sub-shares are the metric's own arithmetic (B is the mean of its timings), not a judgement about importance, and the build refuses to publish if they fail to reproduce the value the scorer stored.

A metric or a criterion that this episode simply does not have — no repair window, no valid detection to time, an episode cut off before any verdict — is shown as not applicable, never as a zero, because “never measured” and “measured and bad” are opposite findings.
