API assistant 是怎么失败的：163 局正式运行的通读审计

formal run v5 · run 1 · 7 个 API seat × 3 persona · 163 局（79 won / 73 wrong serve / 10 burned / 1 timeout）· 28 个读者 · 490 条观察 · 2026-09-24

样本与方法

样本。formal run v5 第一轮，七个 API seat（gpt-6-astra、gemini-3.8-flash、gemini-3.1-pro-preview、gpt-realtime-2.1、gemini-3.8-live，以及两个原生语音 seat gemini-3.8-live__native、gpt-realtime-2.1__native）× 三个 cook persona × 每格至多 8 局，其中一半从失败局抽取——共 163 局。失败局按设计被过采样，下面的百分比是此样本内的占比，不是总体率。

方法。每六局一份 dossier（study_collected_v2/assistant_audit/dossiers/，由 tools/make_assistant_dossiers.py 生成）：订单、persona 及其声明的偏好、注入计划与引擎对每个 flag 的判定、每个脚本问题的 gold 答案与 judge 判定、每个 proactive request 的评分，以及完整时间线——每条 assistant 发言标注「基于哪一 tick 决定、哪一 tick 到达」，装盘与加热事件，引擎的 takeover block。28 个读者 agent 各读一份 dossier，按固定格式为每局写 2–6 条失败观察（mode 句 · aspect · severity · 带 tick 的原文证据），共 490 条（assistant_audit/reading/）。再由 tools/cluster_assistant_modes.py 用多标签关键词规则聚成下面的失败模式（assistant_audit/clusters.json）；页面引用的每个例子都逐字对回 dossier 核对过。计数 = 至少有一条该模式观察的局数。

逐条模式与核对过的例子

1. The assistant warns on the plate, not on the walkperception · timing56/163 局

所有注入错误都留出一段可见的偏离（端着盘子走向错误的 crate，10–30 tick），本意是让 assistant 在 scoop 之前就点破。API assistant 几乎从不这样做：它们把这段路当作正常进度（或继续重复上一步指令），直到错误食材落到盘子上才开口——此时只能倒盘重做。在 live window 的判定下，这正是「可检测」变成 late / missed 的机制。

2. Reply latency makes every line describe a frame that no longer existsperception · timing60/163 局

一条回复基于某一帧决定，3–10 tick 后才到达（API 中位延迟 4–9 s）。厨房里一次 scoop 只要 1 tick，于是话音落地时世界已经变了：让 cook 做它刚做完的事；正确的警告被判 late；最糟的是「别加 X，盘子已经完整——去上菜」在 scoop 之前决定、之后到达，变成对错误的背书。锅上的警告在食材已装盘后到达，被判 false alarm。

对论文的含义

  1. 改变结局的失败以感知与时机为主：模式 1、2、5（commit 之后才发现、过时的帧、按计划而非按盘子说 serve）解释了被审计的大多数 wrong serve；它们是「什么时候看、什么时候说」的失败，不是烹饪知识的失败。
  2. 拉扯循环（模式 9）正是真人研究中决定偏好的因素（57% 的排序），也是这里最高频的观察——两项研究从两侧指向同一个缺陷。
  3. persona 偏好被当成二值开关（模式 12、13）：「别打断」变成哑巴，「一步一步」变成复读；没有一个 seat 会调节阈值。
  4. 监控被交给了语言（模式 3、11）：一句承诺或一句 keep an eye on it 顶替了盯着灶台。
