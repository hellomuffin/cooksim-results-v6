API assistant 还做不到什么：正式运行的能力发现，附 163 局通读审计

formal run v5 · run 1 · 7 个 API seat × 3 persona · 163 局（79 won / 73 wrong serve / 10 burned / 1 timeout）· 28 个读者 · 490 条观察 · 2026-09-24

样本与方法

样本。formal run v5 第一轮，七个 API seat（gpt-6-astra、gemini-3.8-flash、gemini-3.1-pro-preview、gpt-realtime-2.1、gemini-3.8-live，以及两个原生语音 seat gemini-3.8-live__native、gpt-realtime-2.1__native）× 三个 cook persona × 每格至多 8 局，其中一半从失败局抽取——共 163 局。失败局按设计被过采样，下面的百分比是此样本内的占比，不是总体率。

方法。每六局一份 dossier（study_collected_v2/assistant_audit/dossiers/，由 tools/make_assistant_dossiers.py 生成）：订单、persona 及其声明的偏好、注入计划与引擎对每个 flag 的判定、每个脚本问题的 gold 答案与 judge 判定、每个 proactive request 的评分，以及完整时间线——每条 assistant 发言标注「基于哪一 tick 决定、哪一 tick 到达」，装盘与加热事件，引擎的 takeover block。28 个读者 agent 各读一份 dossier，按固定格式为每局写 2–6 条失败观察（mode 句 · aspect · severity · 带 tick 的原文证据），共 490 条（assistant_audit/reading/）。再由 tools/cluster_assistant_modes.py 用多标签关键词规则聚成下面的失败模式（assistant_audit/clusters.json）；页面引用的每个例子都逐字对回 dossier 核对过。计数 = 至少有一条该模式观察的局数。

能力发现（Findings）

每条 finding 是一个关于模型能力的断言，由 benchmark 为每一局记录的量（窗口、tick、判定、配对的免延迟对照臂、rubric）支撑，并以通读审计中逐字核对过的转录作为例证。除特别说明外，数据为七个 API seat 的 run 1（每 seat 150 局）；审计样本是上面的 163 局子集。

F1. Detection is triggered by the outcome, not by the trajectory towards it

每个注入错误都留有一段 commit 之前可见的偏离（端着盘子走向错误的 crate、少一层就走向 serving pass），而同一批模型在盘子事件之后能说出错误，在这段路上却几乎从不开口。七个 API seat 上，第一条正确 flag 的中位位置正好是 commit tick（窗口内位置 1.0）；只有 5–32% 的 commit 前 flag 落在窗口前半段。按错误类型拆开，机制一目了然：偏离表现为台面上一个「状态」的（砧板上切错了东西 0.53；cook 停住 0.35）能被抓住，偏离表现为一段「运动」的（异物 scoop 0.01、生食 scoop 0.03、提前走向 pass 0.07）抓不住——尽管窗口有 7–17 tick，cook 的去向也毫不含糊。现在的模型把画面当作物体状态的快照来读，不把 cook 的运动当作意图的证据。

F2. Reply latency is charged to the world, and the models do not reason about it

一条回复基于某一帧决定、2–8 tick 后到达（各 seat 中位数），而一次 scoop 只要 1 tick。模型从不为这段间隔留余地：把决策帧当作此刻来叙述，命令已经做完的步骤，给话音在途时已经变了的盘子背书。对照臂量化了「时钟」占多大比重：同一批局把延迟设为免费后，commit 前的检测率从 0.30 升到 0.41（GPT-6 Astra）、0.26 到 0.52（Gemini 3.1 Pro）、0.18 到 0.33（Gemini 3.8 Live），in-time success 约翻三倍（实验 4）——但运动型错误即便如此也大多抓不住（异物 scoop 0.01 → 0.12，提前上菜 0.06 → 0.31）。延迟只解释少数漏检，其余是 F1 的决策规则。

F3. A standing request is acknowledged, not kept: proactive alerts fire early, late, or never, with a model-specific bias

「米饭一好就告诉我」是一个必须跨越几十个回合的目标。以食材自己的 done tick 为准（[done, done+25) 内的提示算 in window），七个 seat 表现出三种系统偏差而不是随机噪声：Gemini 3.8 Live 在食材做好之前就报（31% early——把请求当成了「好了吗」来回答），GPT-realtime 2.1 在冒烟之后才报（46% late——提示只是 cook 自己的冒烟报告的回声），两个原生语音 seat 根本不报（51–53% missed——没有人提示它们）。只有 GPT-6 Astra 守住了目标（75% in window）。同一能力也体现在注入的 leave_unattended 错误上：锅里做好的食材是整套 suite 里可见时间最长的隐患（27 tick 窗口），却只有 22% 在冒烟前被点出。

F4. Assertions are not grounded in the frame, and a contradiction from the user does not trigger a second look

false alarm——被引擎判为不成立的错误指控——每局 0.4–3.6 次（每 100 句 5.6–22.5 次）。cook 在六个 tick 内反驳其中三分之一到三分之二；assistant 随后要么道歉再指控，要么用编造的证据坚持（crate 标签、时间戳、关于进度环的规则）。GPT-realtime 2.1 平均每局把同一个 flag 重发四次；Gemini 3.1 Pro 的 false alarm 有 60% 被当场反驳。这正是真人研究中对偏好预测力最强的行为（false alarm 数，pairwise agreement 0.67；57% 的排序由一次错怪决定）——benchmark 的 precision 项和人的判断指向同一个缺陷。

F5. The models answer from the current frame; the stream's history is not retained as state

能从当前一帧回答的问题得分高——牛排煮了多久（Q3，API seat 0.54–0.94）；需要一路跟踪流才能回答的问题得分低：cook 去了几次砧板（Q2，0.13–0.35）、去没去过垃圾桶（Q4，0.30–0.91）、两个备菜步骤谁先谁后（Q1，0.17–0.79）。不问问题时同一缺口也在：倒盘之后世界模型不回滚——随盘子进垃圾桶的食材在 17% 被审计的局里「还在锅里」「还在板上」，cook 被派去从 assistant 自己看着变空的站点舀东西。

F6. A stated interaction preference changes how much the model speaks, not what it judges worth saying

cook 的档案告诉 assistant 它想要逐步指导还是别被打扰。多数 seat 确实会调音量——Gemini 3.8 Flash 对 novice 每 100 tick 说 23 句、对 expert 说 4 句，原生语音 seat 7–8 句对 1 句——而 GPT-realtime 2.1 完全不调（每种 persona 都是 18–20 句）。但这种调节只是说话的增益，不是阈值的改变：expert persona 换来的是毁盘 scoop 全程沉默，novice persona 换来的是复读配方而同样的 scoop 无人提起；要求「积极提醒」的 persona 并没有得到更高的 commit 前检测率（F1）。偏好被实现成「多久说一次」，而不是「什么才是必要的」。

F7. End-to-end speech models answer well but never initiate: the modality removes the trigger, not the competence

两个原生语音 seat 与其文本孪生是同一模型家族，输入是厨房视频加 cook 的语音。它们的 reactive share 是 1.00——每一句都紧跟在 cook 发言六个 tick 之内——于是只有 1% 的错误在 commit 前被点出（文本孪生 17–30%），一半的「好了告诉我」请求被错过，大部分局输在无声中完成的错误上。但只要它们开口，rubric 给的分与文本孪生相当（五类 round-level AQ：GPT-realtime 0.70 对 0.65；Gemini Live 0.72 对 0.73）。缺的是「何时开口」的策略，不是理解力——这与流式视频 benchmark 对 proactive responding 的诊断一致。

对模型研发的含义

  1. 感知必须包含运动：cook 端着盘子的去向是错误最早的证据，目前没有一个模型用到它（F1）。只读物体状态的帧级读者在厨房里做不到 proactive。
  2. 时机是任务的一部分：不建模自身回复延迟的模型会对一个已经变了的世界下指令（F2）；配对对照臂表明延迟只解释少数漏检，单靠更快的推理补不上这个缺口。
  3. 持续目标需要监视器而不是承诺（F3）：三种时机偏差（early / late / never）因模型而异且稳定，是策略的属性而非噪声。
  4. grounding 失败会被用户当场反驳（F4），模型对这种反驳的反应正是人评判的东西；「被反驳后重新看一眼」是可度量、可训练的行为。
  5. 流记忆缺失（F5）：历史问题与倒盘后的规划一起失败。
  6. 偏好条件化被实现成音量旋钮（F6），在语音原生模型上则是开关（F7）：缺的是一个以情境风险、而非 persona 容忍度为条件的「何时开口」策略。

附录 C · 审计自身的小结
