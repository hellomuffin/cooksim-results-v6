Which models we test, and how to run the streaming ones natively

Two questions, answered together. Which models fill the four families of the assistant seat, if each family has five slots. And how each streaming system must be driven so the numbers measure the model rather than our polling loop — because today they do not.

1 · The fairness contract

The benchmark charges wall-clock. A reply's round trip is converted into game ticks (COOKSIM_ASSIST_LATENCY=measured, capped at 30) and the kitchen keeps running while the model thinks. Every setting that changes time-to-speech therefore changes the score, so three quantities have to be controlled or reported per arm.

The three knobs. Anything left uncontrolled here silently becomes part of the result.
knobwhat it iswhy it decides fairness
visual budgetframes/second × resolution × history depthGemini Live is hard-capped at 1 fps; a turn-based model fed 8 frames per poll may see more per decision
decision cadencewho decides when to speakwe poll; a duplex model decides for itself. Polling a proactive model deletes the capability we claim to measure
latency accountingwhat we charge as ticksa voice-native model pays speech-synthesis time; a text model pays none. Charging both the same is a bug, not a control

Report every model twice. A matched arm — 1 fps, identical rulebook prompt, identical flag contract, identical context depth, latency charged from first token — is the apples-to-apples table. A native arm — each system in its best mode, including its own speak decision — is the "what can it actually do" table. The difference between them is the streaming benefit, and it is a more publishable quantity than another leaderboard column. This is where the 2026 literature has landed: VSAS-Bench standardises synchronous vs asynchronous protocols and separates proactiveness from consistency, IPIBench runs every model under one streaming protocol with tolerance windows, and "Don't Pause!" argues for a single-token response design precisely so autoregressive and non-autoregressive systems can be compared without completion latency.

Duplex is cheaper, not dearer. Stateless costs ≈0.76 s and ≈100 output tokens per poll (AWQ). Duplex costs 0.11 s of prefill and, in most windows, one token — so bf16's slow decode barely matters when the modal output length is 1. The catch on our box: the streaming APIs are transformers-only (no vLLM endpoint, hence no AWQ), a 5× decode penalty we accept in exchange for the model's own trigger. Our run also logged the failure modes to report: a false-positive speak on unit 1, and recency bias in streaming mode (it hallucinated frames 9–10 as a continuation).

Qwen3-Omni — be honest that local native is not there yet

MoE thinker–talker. The repo documents batch inference and vllm serve, and evaluates video at fps=2, but no local self-triggering mechanism is documented: real-time interaction is offered through the hosted Qwen3-Omni-Flash realtime API, and local full-duplex is vLLM-Omni experimental. Unless that path works, this model belongs in the matched arm (thinker-only, text out, fps=2), not the native arm. Claiming otherwise would repeat exactly the mistake we are making with the two streaming APIs.

Streamo / Proact-VL — the cleanest match to our own metric

Streamo emits explicit Silence / Standby / Response state tokens; Proact-VL carries a <|FLAG|> response head with transition smoothing. Native use is to read that head per chunk — structurally, our flag field learned end-to-end. They earn a slot each because they let us compare a learned speak decision against the prompted one every other model uses.

4 · What our harness does wrong today

We force every turn. LiveBackend asks with send_client_content(turn_complete=True) on our poll schedule; RealtimeBackend sends an ask per poll. Both models have a native "decide when to speak" mechanism that we never enable. We are measuring them as turn-based models with extra latency — the worst of both worlds.

We charge TTS to the model. Gemini Live is configured for audio output with transcription, so speech synthesis lands in the latency we convert to ticks. Text-native models pay nothing comparable.

We may exceed 1 fps. Anything above the Live API's cap is cost without information, while a turn-based arm gets 8 crisp frames per decision.

We do not serialise. COOKSIM_VOICE_GAP is a floor, not a wait-for-reply. The study app measured 97% of its calls issued while an earlier one was unanswered, so the model could not see its own last line and repeated itself. For a stateful session this is worse than for a stateless one.

Thinking is pinned to minimal on Live while turn-based arms think freely.

Local streaming models get the worst of it. The only local path is --assist-backend openai → a vLLM /v1/chat/completions server: one stateless call per poll, re-prefilling the frames every time, with every trigger head the model owns left as dead code.

5 · What has to be built

  1. A stream backend kind beside gemini/live/openai/realtime: one session per episode, one chunk pushed per tick (or per N ticks so a window ≈ 1 s of game time), read the control token, and materialise an utterance only when the model itself decides to speak.
  2. Latency accounting that does not punish duplex. Charge from chunk arrival to first content token; treat the control token as free. Under today's rule a model answering "listen" sixty times a minute would be billed for sixty replies.
  3. A two-stage output contract. A duplex model will not emit our JSON flag inside a one-token window: the control token decides, then a short grammar-constrained generation produces the flag only when it speaks.
  4. Stop pasting history. The session is the memory; re-sending frames costs prefill and creates the recency bias we measured.
  5. Per-model input specs, not one global setting: MiniCPM-o 448×448 at 1 fps / 1 s windows; StreamingVLM 1 fps interleaved with sinks and windows; Qwen3-Omni fps=2.

Order of work: fix the four API issues → refresh the model IDs (cheap, immediate) → run families A and B in both arms on the existing suite → then the local families, which cost GPU time and can follow. For family D: MiniCPM-o 4.5 duplex first (already stood up here, and its Listen–Speak token gives us the trigger for free), then StreamingVLM (text-out only, simplest session), then Streamo / Proact-VL for the learned-trigger comparison.
