Scope and shared handoff

These briefs support the current Introduction and Methods, not a larger evaluation project. Implementation agents supply existing scores and raw-report paths; we do the paper analysis and figure design afterward. No new runs, paid grading, or recruitment are launched by these documents.

Paper structure

  • Main results: one model-comparison table and one compact interaction-quality analysis. Three-run reliability supports these results rather than becoming a separate experiment section.
  • Validation: a latency comparison, human preference/behavior evidence, and a small user-model comparison. Combine related results into compact panels; put detailed diagnostics in the appendix.
  • The seven folders are work packages, not seven mandatory tables or figures.

Minimum handoff

Reuse engine-native reports. Each agent returns:

  • A short note identifying data paths, case suite, exact model IDs, code/grader version, timing setting, and missing or incompatible data.
  • Relevant episode-level scores in existing JSON or a simple CSV, with case/model/repeat identifiers and original-report paths. Retain counts or eligibility for rates; unsupported metrics stay missing.
  • A few observations and linked examples where requested.

Raw conversations and state dumps can stay in their current directories. Supply the existing aggregation command/script; add a small extractor only for a genuinely missing field. No new logging system, duplicate exports, publication figures, or exhaustive annotations are required. Keep identifiable human records and recordings out of the paper repository.

Existing resources

Paths are relative to the workspace.

  • CookSim: cook-bench-engine/tools/eval_composite.py, current benchmark reports, and tools/sq_v4_score.py for round-level quality. The older run_qual_eval.py is a different evaluator; do not mix its scores into the current rubric.
  • VHSim: vh-streaming-engine/tools/assist_metrics.py and current tmp/bench_v1 reports. The evaluator explicitly leaves QA/alerts unmeasured; do not invent results for table completeness.
  • ScreenSim: screensim/tools/bench_3runs.py already aggregates three runs; verify the run roots before reusing them. Its current loop waits for the assistant: latency is recorded but does not advance phone state.
  • Human study: existing study_collected exports, study_collected/audit/extract_behavior.py, and cook-bench-engine/tools/sq_v4_human.py. The September 18 audit is a starting point, not a current conclusion.
  • User-model probes: sections/experiments.tex, tables/human_agent.tex, and cook-bench-engine/docs/probe_results/. Reuse compatible designs, not historical scores.

Scope and order

01 supplies rollouts to 02 and 03. Analyze existing human data jointly for 05–06 before deciding what 07 needs.

Main results use measured assistant delay where implemented; describe ScreenSim's existing turn-based policy separately.

Do not mix old/current suites or launch replacement sweeps just to match these briefs. First report reusable outputs and specific missing runs.

No required persona/difficulty cross-tabulation, fixed-delay sweep, new judge panel, learned preference score, or exhaustive significance-testing package.

Validation · Work package 4

How much does assistant delay affect performance?

Test the Methods claim that responses can become stale while the user and environment continue acting.

Agent delivery

  • Start with CookSim's implemented measured-delay versus delay-off settings. Reuse compatible measured-delay runs; pair them with fresh delay-off rollouts on the same cases and assistant/user settings.
  • Propose a small assistant subset covering different measured response speeds and the missing-run budget first. No fixed-delay grid is required.
  • Return case-level success and detection timing in both conditions, recorded response delays, and two or three late-advice examples with observation/delivery ticks.
  • Add VHSim only if comparable runs exist or a concrete gap warrants them. Exclude ScreenSim: its current loop waits for the assistant.

Our analysis / paper output

One paired plot or compact table showing performance and ordering within the tested subset, with examples of stale advice or missed intervention windows.

Do not re-time a saved transcript and call it a rollout. No automatic validity labels for every response, new scheduling mechanism, or full-roster rerun.

Validation · Work package 6

How do simulated users resemble and differ from people?

Support the human-agent design with behavioral evidence and identify limitations, including excessive replies or next-step narration.

Agent delivery

  • Use 05's human collection and the closest existing simulated CookSim episodes. Record task/assistant/prompt versions and whether events were forced.
  • Start with study_collected/audit/extract_behavior.py and existing outputs. Return a small comparison of task success, observed execution mistakes, speech frequency/length, reply frequency, and unsolicited next-step narration.
  • Retain per-episode values and denominators for quantitative measures. For mistakes and wording, a few trace-linked examples are enough initially.
  • Exclude forced actions/scripted utterances from spontaneous-behavior counts. Filtering does not undo their downstream effects; disclose this and use uninjected episodes where available.

Our analysis / paper output

One compact human-versus-simulated comparison and a short limitations paragraph. Match tasks/assistant conditions where possible; do not attribute differences automatically to the user model.

Compare conversational behavior and function, not exact wording, and do not presuppose realism.

If existing simulations cannot support a fair comparison, propose a small matched collection. No exhaustive action/speech annotation set or reproduction of every old audit statistic.
